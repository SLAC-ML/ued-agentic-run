UED · Osprey / Otter deployment
Investigated 7 Oct 2026 · read-only checks on ued-daq

Osprey and Otter can run on ued-daq straight from S3DF

ued-daq mounts the S3DF group and home areas read-write at the same paths, and it reaches the SLAC AI gateway without a proxy. So none of the LCLS steps (staging, path rewriting, pushing, cutting over) is needed for UED. We build on S3DF and launch on ued-daq.

No copy needed

The existing builds start on ued-daq in place: Osprey 2026.6.2 on Python 3.12, Otter's venv on Python 3.11, and the bundled Claude Code 2.1.281. /sdf/group and /sdf/home are NFS read-write there, and the home directory is the same one as on S3DF.

No tunnel needed

ued-daq reaches ai-api.slac.stanford.edu directly; the gateway answers "No api key passed in". For anything outside SLAC, the PCDS proxy psproxy:3128 works.

The LCLS proxy isn't for us

lcls-prod03:3128 accepts the connection, then answers 403 Forbidden. Its squid only serves the LCLS hosts.

What ued-daq can reach

HTTPS requests from ued-daq without credentials. A 401 means the request reached the service, which then asked for a key.

LCLS vs UED

The LCLS route exists because lcls-srv01 can't see S3DF.

How LCLS deploys (deploy/acr)

  1. stage.sh builds a 9.4 GB tree on S3DF.
  2. rewrite_staging.sh swaps every /sdf/… path for /usr/local/lcls/tools, and verify_staging.sh proves none is left.
  3. The tree is pushed with rsync from mcclogin to lcls-srv01.
  4. acr_cutover.sh carries over local state and repeats the proofs.
  5. LLM traffic goes through HTTPS_PROXY=lcls-prod03:3128, set in profiles/lcls-acr.yml and in Otter's launch_acr.sh.

What UED keeps and drops

  • Keep: a host profile variant (ued-daq) for the network and EPICS settings.
  • Keep: a launcher that unsets PYTHONPATH. ued-daq's setup_env.sh sets one, just as the ACR shell does.
  • Keep: offline web assets (OSPREY_OFFLINE=1), the longer MCP timeouts, and a web terminal on loopback reached through an SSH tunnel.
  • Drop: staging, path rewriting, the push and the cut-over. The paths are already right on ued-daq.
  • Drop: the corporate proxy for the gateway; the direct route works.

Plan

  1. Create the UED deployment repo at OspreyDeployments/UED on S3DF, modelled on LCLS, with a ued-daq variant:

    provider: slac  →  https://ai-api.slac.stanford.edu/v1   (SLAC_API_KEY in .env, mode 600)
NO_PROXY=localhost,127.0.0.1,ai-api.slac.stanford.edu     # the gateway, direct
HTTPS_PROXY=http://psproxy:3128                            # anything outside SLAC
OSPREY_OFFLINE=1
control_system.writes_enabled: false                       # read-only, as for LCLS

    The read-only beamline snapshot from bringup/ becomes its first machine tool.

  2. Build on iana with osprey build. It writes only to S3DF.

  3. Add a launcher, deploy/ued/launch_ued.sh. It unsets PYTHONPATH, puts the build's venv first, and points the web terminal at the bundled claude.

  4. Smoke-test on ued-daq, in this order: launch_ued.sh health, then launch_ued.sh chat --print ping (one round trip through the gateway), then the web terminal. The existing ued-daq SSH alias already chains s3dflogin → psdev → ued-daq, so the tunnel is one line:

    ssh -L 10102:127.0.0.1:10100 ued-daq     # then open http://localhost:10102

  5. Otter: add a ued host case to its launcher, with the same network settings. Its venv already runs on ued-daq.

Decisions for you

  • AccountRun as zhezhang (works today) or uedopr? uedopr's home is also on S3DF, but it would need read access to the tree and its own key file.
  • Write safetyued-daq can write to every hutch IOC directly over Channel Access. Besides writes_enabled: false, the agent's shell permissions should deny caput and pvput. A read-only CA gateway would be the stronger fix later.
  • Accelerator PVsStill reachable only from testfac-srv01. Until that's settled, the UED agent sees the hutch only.
  • S3DF dependencyRunning in place means an S3DF outage stops the agent. A local copy on ued-daq would avoid that, but needs writes there, which would be yours.
  • psproxyWorth a quick check with PCDS IT that the agent may use psproxy. It's only needed for traffic outside SLAC, such as api.anthropic.com.
